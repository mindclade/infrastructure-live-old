# Publish and renew RFC 9116 security.txt

> **Audience:** Platform, DNS, and security operators
> **Outcome:** Serve the reviewed security contact policy from every controlled HTTPS origin,
> retain connected evidence, and renew it before expiration.

## Safety and authority

`contracts/security-txt.json` and the generated files under
`3-networks/shared/security-txt/` are publication inputs. Committing them does not publish an
endpoint and is not evidence that an HTTPS origin is healthy. Cloud DNS cannot serve an HTTP
resource; the Platform-owned edge or site origin must map the exact generated bytes to
`/.well-known/security.txt` without redirects to another domain.

Publication does not grant permission to test Mindclade systems. The vulnerability-reporting
scope, safe-harbor limits, and third-party boundaries remain in the linked security policy and
applicable agreements.

## Generate and review

1. Update `expires` to a UTC timestamp no more than 366 days ahead. The validator begins failing
   30 days before expiry so renewal cannot silently become an incident.
2. Confirm `security@mindclade.com` is monitored and the public Policy URL is reachable.
3. Regenerate and review all four files:

   ```sh
   python3 scripts/validate_security_txt.py --write
   git diff -- contracts/security-txt.json 3-networks/shared/security-txt
   ```

4. Obtain the required Legal, Security, and Platform approvals. Do not clear an activation
   blocker on source evidence alone.

## Publish

For each of `mindclade.com`, `mindclade.ai`, `mindclade.dev`, and `mindclade.studio`:

1. Configure the owning HTTPS origin to serve its domain-specific generated file at the exact
   `/.well-known/security.txt` path with `Content-Type: text/plain; charset=utf-8`.
2. Preserve the generated `Canonical` URL for that domain. Do not use a cross-domain redirect as
   a substitute for the canonical resource.
3. Fetch the endpoint from an external network and compare its SHA-256 and bytes with the
   reviewed file. Verify the TLS certificate, status `200`, content type, and caching policy.
4. Record timestamped response headers, body digest, certificate identity, source commit, and
   checker identity in the approved evidence system.

Only after all four origins and the Policy URL pass may an operator change `publication.status`
to `published`, clear every blocker, and add the immutable connected-evidence URL and verification
timestamp. That change goes through the normal protected infrastructure workflow.

## Diagnose failure

- `404` or wrong content: verify edge routing and deployed source revision; DNS changes will not
  repair an origin mapping.
- Redirect to a different domain: serve the domain-specific file locally and retain its exact
  `Canonical` field.
- TLS error: stop publication qualification and follow the certificate/DNS runbook.
- Expired content: publish a reviewed future expiry immediately; do not extend the date only in
  the live origin without updating source.
- Body mismatch: roll the origin back to the last reviewed artifact and investigate deployment
  provenance.

## Renewal and rollback

Renew at least every six months and before the 30-day validation threshold. If a newly published
file is malformed, restore the last unexpired reviewed bytes at the same origin path. Preserve
both response captures and the change or incident reference; never delete the endpoint during a
contact-policy rollback.
